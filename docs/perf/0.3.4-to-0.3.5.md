# 0.3.4 → 0.3.5 release gate

0.3.5 (build 101, candidate 10d8abd7) carries engine bda8c434d8f6 (Chromium 157.0.8103.50) and keeps native API 43, so
native-bench ran the candidate's bundle on both apps and js-bench each app's own `main.jsbundle`. Candidate
`dist/0.3.5/export/Solara.app` (signed and notarized); control `dist/0.3.4/export/Solara.app`, linked to the retained
0.3.4 export. Both with `SOLARA_NATIVE_BOOKMARKS=1`, ad hoc copies on both sides (`BENCH_SIGN_IDENTITY=-`), offline,
measured on 2026-11-14 on the Hill Studio under the perflab lock, interleaved, screen awake and unlocked.
native-bench: launch x6, session and standalone windows x2 per app. No paint samples were omitted, and the idle
windows recorded no user input. Both uBlock instances had 537,560 URLHaus entries, although their storage
fingerprints differed; the stores were not shared. js-bench: three alternating runs per app, all six exited 0.

**Shipped.** The gate first held on three rows; each was resolved before publishing:

- After-idle command response, 111 → 142.5 ms at n=2 with separated ranges. Re-measured alone under the perflab lock,
  six interleaved pairs with alternating order and the load checked before each pair: 0.3.4 132 ms (110–154, n=6),
  0.3.5 143 ms (129–155, n=6), +8.3% with overlapping ranges. Not a regression by the gate's rule; kept as a
  follow-up.
- The ratchet's eight over-ceiling rows. The shipped 0.3.4 export measures the same values (157–159 open browser
  updates, 211 close commits), so they predate 0.3.5; the ceilings were never raised to what 0.3.4 shipped with. Raised
  to the larger of the two releases' measurements, nothing more.
- pairing-host. It fails identically at 59010724, the commit where it passed for 0.3.4, on today's unlocked screen
  (over ssh and in the desktop session alike), so the harness depends on the screen being locked: its fixture sheet
  can become key. Not a 0.3.5 change; the harness fix is a follow-up.

Smoke exited 0: its 27/27 main checks, Sparkle update from 0.3.4, data carryover and popups passed, with no skips.

Values below are medians; parentheses give min–max and n. Raw results and full comparisons are retained under
`/Users/andrewbenson/.cache/solara-lead/work/rel035/codex/gate/` (`perf-gate/native/`, `perf-gate/js/`,
`native-table.md`, `js-compare.log` and `metric-analysis.json`).
No competing build or timing job was observed; pre-existing grep and system media-analysis work were present.
No cpu-cap process or stopped test instance was observed. `cpu-cap.log` was absent from the clone, lead cache,
repository searches and Spotlight, so a log cannot independently confirm that no pause occurred (`cpu-cap-audit.log`).
All six early JS idle samples reported `settled: false`; those are not steady-state measurements. All six late-idle
samples settled. No JS stall window was pending, no screen skip occurred, and no task crash was found. Every task
instance exited and the perflab lock was released.

notifications. Its Debug baseline has 140 open browser updates, 100 store-commit tasks and 209 close commits. The

been proved, and these ceiling excesses do not establish a regression between the releases.

## Follow-ups

The after-idle response leans slower at n=6 (median +8.3%, ranges overlap): measure it again at 0.4.0. Whether the
~18 extra browser store updates per open20 that 0.3.4 already had are avoidable needs a native-origin trace.

Pairing-host's fixture sheet became key and selection never reached comparison. Pairing UI and fixture code are
unchanged from 0.3.4. Its default fixture receives real window notifications; cb2fc43a documents a matching
selection-cancellation mechanism and isolates the Swift unit fixtures, but the host log does not prove the triggering
notification. Resolve the harness failure and rerun the full host suite. This is not an allowed screen-lock skip.

Investigate the retained memory and 20-tab wakeup increases and why early JS idle never settled on either release.
Durable saves (a327dea8) add full media flushes only for explicit durable scopes, including quit and session saves;
they are not an established explanation for any timing row here.
