# 0.4.1 → 0.4.2 release gate

0.4.2 (build 104, release `adad9cbb`) keeps Chromium 157.0.8103.50 and moves native API 65 → 66.
Native window layout stays off by default in both releases. The supplied candidate
`dist/0.4.2/export/Solara.app` is signed and notarized; `dist/0.4.1/export/Solara.app` matches the retained
0.4.1 control’s code hash. native-bench used the candidate’s bench bundle and the retained API-65 control bundle;
js-bench used each app’s own shipped `main.jsbundle`. Both with `SOLARA_NATIVE_BOOKMARKS=1`, ad hoc copies on
both sides (`BENCH_SIGN_IDENTITY=-`), offline, measured on 2026-11-16 on the Hill Studio under the perflab lock,
interleaved, with `caffeinate -d`. native-bench: launch x6, session and standalone windows x2 per app.
js-bench: three alternating runs per app, all six exited 0.

also blocks release. The rule has no absolute-time floor, so the two sub-millisecond rows below count.

No timing increase has a verified commit-level cause. The after-idle command row includes a deliberate 100 ms
timeout, app-side command polling every 50 ms, file IPC and driver-side response polling every 20 ms. Its timer’s
lateness stays 0–2 ms in the control and 2 ms in the candidate. The approximately 20 ms roundtrip increase could
be one polling quantum, but no command pickup/completion timestamps were retained to prove that explanation.
It remains a blocking measured row. App Nap was disabled on both sides by the bench’s default.

The JS startup row measures bundle start → the first native chrome Core Animation commit (mark revision 2),
within the big-session instrumented JS scenario. It is distinct from native-bench’s small-session launch →
window-shown row. The typing row times the synchronous omnibox driver call for each growing query string;
the profile-swipe row times synchronous `nextProfile`/`previousProfile` command dispatch, not the full animation
or its 1500 ms settling period. Their absolute increases are small, but all four rows meet the stated hold rule.
The known feature commits and attributed ratchet counts do not establish a causal timing explanation.

## Same or below the hold threshold

Native launch → window shown is 827 → 893 ms (+8.0%, overlapping ranges); launch → first page painted
1164 → 1228 ms (+5.5%, overlapping ranges). New tab → first paint is 102.9 → 99.7 ms with overlapping ranges.
New window → on screen is 131 → 138 ms and → first paint 159 → 161 ms, both with overlapping ranges.
Native total idle CPU and wakeup ranges overlap. Memory is diagnostic only with two session runs per side: total
footprint is 356 → 367 MB at one tab and 982 → 1008 MB at twenty tabs. The perf guide requires at least four
runs per app before gating memory; these two-run differences are not release regressions.

JS launch → bundle start rises 3553 → 3703 ms (+4.2%) and launch → first native chrome commit
3926 → 4131 ms (+5.2%), both separated but below 15%. Bundle evaluation stays 26 ms. Open20 task time
2085 → 2050 ms, close20 task time 927 → 961 ms, and close20.otherJsMs 405 → 424 ms all have overlapping
ranges. Profile-swipe total JS task time falls 239 → 146 ms, but ranges overlap, so no improvement is claimed.
The startup, idle, switch, scroll, page-load, hover and profile-swipe stall-time ranges also overlap.

The native raw stall collector’s six launch-phase startup windows rise from 366 ms (345–591) to
442 ms (430–448), and its cumulative launch stall totals from 386 ms (360–606) to 460 ms (450–465);
ranges overlap. Separately, the two session-startup diagnostic windows rise 353 ms (347–360) →
424 ms (408–439), with separated ranges. These are collector windows rather than official native summary rows;
they must not be pooled with the six launch samples or interpreted as per-action latency. Keep them as a
startup follow-up alongside the blocking JS startup row.
