# 0.0.1 baseline

0.0.1 is the first Solara release, so its perf gate had no earlier stable to time against (releasing.md). Its numbers
are recorded here instead. The next stable is gated against this page together with 0.0.1's own export.

- **Build:** the published `Solara-0.0.1.zip` from the v0.0.1 GitHub release, sha256
  `2c2da1e3ac2ef1076ac619d394c7ed48a2c30c26eef4390908955feaf2de6c61`. It's ad hoc signed, bundle `com.hill.solara`.
  Rerun with the same zip, not a rebuild.
- **Tools:** the benches came from the v0.0.1 tag (7f81a25b). Their bench bundle matches 0.0.1's `NATIVE_API_VERSION`
  of 32; today's tree is a later version, and its bundle would fail with "Native API skew". The app was built from
  450f47cf, and nothing under apps/browser or packages changed between that and the tag.
- **Machine:** measured on 2026-11-01, 06:40–06:59, on the Hill Studio. No builds, tests or other instances were
  running. The load (1-minute average) is given next to each bench below.
- **Control:** 0.0.1 ran alone.

## Locked screen: tab switch and new tab are provisional

The Hill Studio's console session was locked for the whole run (`CGSSessionScreenIsLocked` true before and after).
While the screen is locked, macOS gives windows no display-link frames, and pages paint about once a second
(README, "Use a quiet machine"). That drives exactly the two rows that time a page's paint after an action: **tab switch
→ shown** and **new tab → first paint**. They are recorded below as **provisional (screen locked)**, and nothing is gated
on them until an unlocked rerun replaces them. In this run native-bench counted 0 "samples left out", so frames did
arrive; the rows are held back anyway, because a locked session doesn't guarantee them. Launch, idle CPU and wakeups,
memory, new window and the js-bench counts don't depend on display-link frames.

## js-bench

Three runs, `js-bench.mjs run --app <0.0.1> --bundle <0.0.1>/Contents/Resources/main.jsbundle --runs 1 --append 1`,
each with
`--scenarios startup,persistence,idle,typing,switchTabs,openClose,pageLoad,storeUpdate,idleLate`, 06:54–06:59. Medians
[min–max] of 3. The load was 2.4 before the first run, 3.5 after it, 4.1 after the second and 2.9 after the third.

That load is high for timing, so treat the millisecond rows here as a noisy floor: a later run on a quiet machine may
come out faster, and the next quiet window reruns js-bench to replace them. The counts (commits, renders, store updates,
timers, writes) don't move with load.

The tag's `bench-app.js` can't run three of its scenarios on 0.0.1, because they drive the React sidebar that 0.0.1's
native sidebar replaced. `scroll` stops with "no current SidebarPage", `hover` with "only 0 hoverable rows", and
`profileSwipe` drives the same sidebar. They're left out here.

**The ratchet has no result for 0.0.1.** `ratchet.mjs run --own` runs a fixed journey list that includes `scroll` and
`hover`, so it stops at the same point (exit 2). The backlog row "bench-app.js's scroll, hover and profileSwipe scenarios
drive the React sidebar" covers moving those scenarios to the native sidebar; until it lands the ratchet can't gate a
native-sidebar build.

## Rerunning

Use the same zip, check it with `shasum -a 256 -c`, and run the benches from the v0.0.1 tag, with the screen unlocked, the
display awake (`caffeinate -dis`) and the load under 1.5. That run replaces the provisional rows and js-bench's
millisecond rows. When the next stable is gated,
run 0.0.1's export as the control, interleaved, with its own bench bundle (`--control-bundle`, built from the v0.0.1
tag), as the README describes.
