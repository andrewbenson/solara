# 0.3.0 → 0.3.1 release gate

0.3.1 moves the engine to Chromium 157.0.8103.50 on Helium 0.21.2 (engine 574046ecf2af); both apps speak native API
40, so native-bench ran the candidate's bench bundle on both sides, and js-bench ran each app's own `main.jsbundle`. The
candidate is `dist/0.3.1/export/Solara.app` (signed and notarized, built from 2ca331ed); the control is
`dist/0.3.0/export/Solara.app`. Both run with `SOLARA_NATIVE_BOOKMARKS=1`. Measured on 2026-11-11 on the Hill Studio
under the perflab lock, ad hoc copies on both sides (`BENCH_SIGN_IDENTITY=-`). The screen was locked, so every row that
waits on a paint or a frame reads pending.

## Result

Every row is the same within noise or better except one: the browser process alone is 2–4 MB larger, in both session
rounds. The whole app is a quarter smaller.

- **Launch** (launch x6): window shown 621 ms (516–672) → 620 ms (563–658); JS running 504 ms (496–611) → 509 ms
  (493–658). Overlap.
- **New window:** on screen 84 ms (76–92) → 83 ms (74–92). Overlap.
- **Idle:** CPU and wakeups overlap in every row; renderer wakeups at 20 tabs 11.5 (11.5–11.6) → 10.5 (10.4–10.7).

| browser process, after closing | 168 MB (168–168) · 169 MB (168–169) | 171 MB (170–171) · 171 MB (171–171) |

Both sides had the same process count at every step (7, 16, 26, 7), classified by `--type`, not by helper name. The
saving is in the child processes Chromium 157 starts from its Aperitif helpers: renderers about 22 MB per tab against
36 MB, the network and storage services about 10 MB and 6 MB against 22 MB and 18 MB, the extension process 104 MB
against 118 MB. The browser process grows by 3 MB with 20 tabs and 2 MB after closing them; no Solara change in this
release adds browser-process state that scales with tabs (the hover-card cap removes some), so it's taken to be
Chromium 157's.

## JS (js-bench, three alternating runs each)

Three rows separated in the gate round: open20.otherJsMs 2782 (2679–2860) → 2932 (2912–2941), open20.taskMs 3217
(3120–3302) → 3368 (3344–3377), idle10s.taskMs 17.0 (14.7–17.1) → 17.9 (17.9–28.3). Every other row overlaps
(startup.launchToFirstWindowMs 3535 → 3453, switch12.taskMs 521 → 536, close20.taskMs 734 → 749).

None of the three reproduced. Codex job open20 then ran the same two apps ten more times, interleaved, under the perflab
lock: open20.otherJsMs 2814 (2793–2831, n=4) → 2766 (2665–2937, n=6), open20.taskMs 3261 (3228–3273) → 3209
(3107–3390), idle10s.taskMs 19.3 (18.4–20.6) → 19.8 (18.5–23.2). Engine swaps in the same session: the 0.3.1 app on the
156 engine read open20.taskMs 3135 (3112–3275, n=3), overlapping 0.3.1 as shipped; the 0.3.0 app on the 157 engine
read 3298 (3274–3322, n=2), one millisecond clear of 0.3.0 as shipped on two runs, and inside the shipped 0.3.1 range.
A 0.3.1 build without the focus-restore retry (75f1af4a) read 3231 (n=1). The job hit its time limit before writing
its own diagnosis; these are its raw logs.
