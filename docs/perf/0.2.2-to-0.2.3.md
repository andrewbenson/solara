# 0.2.2 → 0.2.3 release gate

0.2.3 adds the launch ad hold (restored tabs wait for uBlock Origin, cb8a5d6b), the Picture in Picture fixes and
engine 8b4ed49dd1de (PiP v3, free-move, native API 37), and the first two tab-sleep landings (off by default). 0.2.2 is
native API 36 and 0.2.3 is API 37, so native-bench ran the control on its own bench bundle, built from 0.2.2's tree
(2eeeb05a) and kept as `dist/0.2.2/bench/main.jsbundle`; js-bench runs each app's own `main.jsbundle` (both Hermes
bytecode v96). The candidate is `dist/0.2.3/export/Solara.app` (notarized, built from aa022936); the control is
`dist/0.2.2/export/Solara.app`. Measured on 2026-11-04 on the Hill Studio under the perflab lock and a QUIET window:
native-bench interleaved (launch x6, session x2, windows), then js-bench in two rounds of 3 alternating runs (control
first, then candidate first), ad hoc copies on both sides (`BENCH_SIGN_IDENTITY=-`). The screen was locked, so every
row that waits on a paint or a frame reads pending.

## Result

Every gated row is the same within noise once the ad hold's cost is set aside, and the hold's cost was accepted:

- **launch → JS running: 427 ms (406–544) → 480 ms (446–492), +53 ms, overlapping.** The hold accounts for it: a
  same-base pair (ad33c57a with and without cb8a5d6b, local Release) gave 369 → 425 ms (+56 ms, separating), because
  uBlock Origin's page and readiness call now run at launch instead of 1.5 s later. The owner accepted the hold at
  about +263 ms to a restored tab's DOMContentLoaded (cb8a5d6b).
- **Idle CPU, 1 tab:** browser process 0.98 % (0.98–0.99) → 1.31 % (1.05–1.57) separates in this round, and all
  processes just does (2.39–2.48 against 2.49–6.58). The control sits below every earlier 0.2.2 and 0.2.1 run
  (1.2–1.7 %), and in the first 0.2.3 gate the same rows overlapped with 0.2.3 lower on all processes (5.87 against
  4.78 %). Not reproduced across the two interleaved rounds, so not a regression; watch it next gate.
- **New tab → DOM ready** (informational) separates, 83 → 87 ms. It gates nothing.
- **js-bench:** bundle eval is unchanged (64 against 62 and 66 ms); first commit and first window come about 30 ms
  sooner (bundleToFirstWindow 144 → 116 and 148 → 116 ms), and startup does far less work (taskMs 1290 → 598 in
  round 2, renders, host updates and store updates 13 → 10 lower in both), because restored tabs wait once instead
  of updating twice. profileSwipe.taskMs separated in round 2 only (114 → 124 ms).
- **Ratchet:** ok. Run 1's only count over was noisy typing.tasks, 165 against 164; it didn't repeat in run 2. Hover is
  pending (locked screen).

No `## Faster` section: the faster startup rows come with the hold, not an optimisation.

## The first gate, and the bisect

The first 0.2.3 build (ff26fbdc) failed the gate: launch → JS running 423 → 542 ms (+119 ms, separating), browser
memory +7–8 MB, and js-bench's startup.bundleEvalMs doubled (65 → 128 and 135 ms) in both rounds. Same-base pairs split
it:

- the hold: +56 ms of launch → JS running (above), no memory change (154 against 155 MB at 20 tabs), no bundle-eval
  change (66 against 68 ms);
- tab sleep landing 2 (9467e594): ff26fbdc against ff26fbdc with 9467e594 reverse-applied, on the same engine, gave
  bundle eval 67 → 133 ms, first commit 115 → 150 ms. StoreModule's synchronous `status()` now read the runner's state
  through `DispatchQueue.main.sync`, and the store calls it while the bundle evaluates, so the JS thread waited for a
  main thread busy with launch. aa022936 reads it from a lock-protected mirror instead; this rerun shows bundle eval
  back at 62–66 ms.

The rest of the first gate's launch → JS running gap and its memory step don't reproduce on aa022936, so nothing was
bisected further (tab sleep landing 1, the PiP app work and the engine change stay unbisected).
